## 1. 共用约定（两个任务都必须遵守，验收时会查）

### 1.1 模拟的三条铁律（摘自排期 §3.5 设计要点 2/3/6，不可协商）

1. **只替换"外部调用的那一次网络请求"**——前端页面、交互流程、状态流转、数据库落库、审计记录全部走真实链路。观众在演示现场不应能看出是模拟的。
2. **每个模拟能力必须有审计记录可查**。T41 / T42 对应链路图 §3.3 的四条审计闭环中的 ①②。
3. **前端统一打「模拟环境」角标，主动说明而非掩盖**。

### 1.2 Provider 抽象层的统一形态

```
业务代码 / 前端 / 数据库
        │   （完全不知道底下是真是假）
        ▼
   Provider 抽象接口       ← app/providers/{sms,face}.py，定义能力契约
        ├── MockSMSProvider / MockFaceAuthProvider    ← 当前使用（`.env` 开关选中）
        └── RealSMSProvider / RealFaceAuthProvider    ← 未来，同一接口，上层零改动
        │
   注入方式：FastAPI 依赖  get_sms_provider() / get_face_provider()  ← app/providers/deps.py
   切换方式：.env 一个开关  SMS_PROVIDER=mock|aliyun   FACE_PROVIDER=mock|tencent
```

**禁止出现的写法**（这类代码在答辩时一眼就会被判定为"假实现"）：

```python
# ❌ 反面：Provider 没抽出来，模拟逻辑散在路由里
@router.post("/auth/sms/send")
async def send(phone: str):
    code = "123456"          # 写死
    return {"code": code}    # 把验证码返回给前端
```

```python
# ✅ 正面：路由完全不知道底下是 mock 还是真实
@router.post("/auth/sms/send")
async def send(body: SmsSendIn, sms: SMSProvider = Depends(get_sms_provider)):
    await sms_service.issue(phone=body.phone, scene=body.scene, provider=sms)
    return ok(data={"cooldown": 60, "mock": settings.SMS_PROVIDER == "mock"})
```

### 1.3 与 T11 审计中间件的接口（两个任务都要提交这张清单）

T11 的兜底层会自动记录所有 POST/PUT/DELETE。但登录相关请求的 body 里含**密码与验证码**，必须由 T41/T42 向 T11 提交**敏感字段名单**，否则会污染审计表：

| 字段 | 出现在 | 审计中的处理 | 理由 |
|------|--------|-------------|------|
| `password` | `POST /auth/login` | **永不落库**，`detail` 中记为 `"***"` | 密码任何情况下不得进日志 |
| `code`（邮箱/短信验证码） | `verify` 接口 | **mock 环境落明文**，真实环境记 `"***"` | 排期 §3.5 要点 3：演示需要从审计页读到验证码 |
| `phone` | send / verify | 落库前脱敏为 `138****1234` | 对应 T38 脱敏要求 |
| 人脸图片二进制 | `face/enroll` / `face/verify` | **不落库**，只记 `file_name` / `size` / `md5` | 生物信息不进审计 |

> **交集**：`code` 明文落审计是"模拟实现"专有的演示需要（链路图 §3.2 判据②要求"验证码可在审计页查到明文"），真实接入时必须改为脱敏。**这条要在代码里写成显式开关，不能靠人记得改。**

## 2. ⚠️ 三个必须先定口径的设计冲突

> 这三处是上游三份文档在交叉阅读时暴露出的不一致。**不先定下来，T41/T42 的验收会当场吵起来。** 建议在 Day 1 启动会上一并拍板（10 分钟）。

### 冲突 1：人脸 Mock 的判定逻辑，满足不了"换人脸不通过"的判据

- **排期 §3.5 要点 6 写的是**：`MockFaceAuthProvider` 按「已录入人脸 + 请求照片非空」判定。
- **链路图 §3.2 判据 ⑤ 要求**：「换人脸不通过」。

**这两条直接矛盾**——按"非空即通过"的逻辑，随便传一张图都会通过，判据 ⑤ 永远无法满足。演示时验收人拿另一位医生的照片一试，系统照样放行，这项直接判不合格。

**建议方案（推荐 A）**：

| 方案 | 判定逻辑 | 能否过判据⑤ | 工时影响 | 说明 |
|------|---------|------------|---------|------|
| **A. 感知哈希比对（推荐）** | Pillow 计算 8×8 dHash，与已录入图片的汉明距离 ≤ 20/64 判通过 | ✅ 能 | +0.5h | 真的做了"图像特征提取 + 比对"，答辩时是加分项，不是掩饰；Pillow 已随图片处理依赖引入，零额外成本 |
| B. 仅"已录入 + 非空" | 按排期原文 | ❌ 不能 | 0 | 需把判据 ⑤ 改为"未录入人脸的用户校验 → 失败" |

**若选 A**，需同步修订：排期 §3.5 要点 6、链路图 §3.2 第 2 行。答辩口径改为：「模拟实现不做活体检测，但真实执行了图像特征比对；接入腾讯云人脸核身时替换为服务端比对 + 活体检测。」

> ⚠️ 方案 A 的已知局限：同一人的两张不同角度照片，dHash 距离可能接近阈值上限。**缓解措施**：阈值放宽到 20；演示账号提前用**同一设备、相近角度**采集录入图与校验图；准备失败时的提示文案为「未匹配到已录入人脸，请调整光线后重试」而非"识别失败"，避免演示翻车。

### 冲突 2：人脸图落 `uploads/`，与 StaticFiles 静态挂载直接冲突

- **需求 §5.1 写的是**：文件存储「本地磁盘 `uploads/`（**FastAPI StaticFiles 提供**）」。
- **链路图 §2.2 判据要求**：「人脸照片不可直链——拿到返回的图片标识，尝试不带 Token 直接访问 → 返回 401/403，**不存在可猜测的静态 URL**」。

**如果 `uploads/` 整个目录被 StaticFiles 挂载，人脸图就一定能被 `/uploads/face/xxx.jpg` 直链访问**，这条判据必然挂掉，且属于安全类失分（PPT slide 9 的 Strict Privacy Isolation）。

**建议方案：按可见性分目录，只挂公开的那一半。**

```
uploads/
├── public/                 ← 只有这个目录被 StaticFiles 挂载（问诊图片、会诊资料）
│   ├── chat/               →  /static/chat/{uuid}.jpg
│   └── meeting/            →  /static/meeting/{uuid}.pdf
└── private/                ← 绝不挂载，只能通过鉴权接口读取
    └── face/               →  GET /api/auth/face/image/{ref}   （带 Token，仅本人/admin）
```

**改动清单**：T26（图文消息）、T31（会诊资料）的上传路径改为 `uploads/public/...`；T42 用 `uploads/private/face/...`。需同步修订需求 §5.1 的措辞。

**配套要求**：
- 对外只暴露 `face_image_ref`（形如 `f_9a3c2e1b`），**不含目录、不含扩展名、不含用户 ID**——无法从 ref 反推路径，也无法枚举。
- 磁盘文件名为 `{uuid4}.jpg`，与 ref 的映射关系由 `user.face_image_ref` 承载。
- 目录遍历防护：`ref` 必须严格匹配 `^f_[0-9a-f]{8}$` 正则后才查表，拒绝任何含 `/`、`..`、`%2e` 的输入。

### 冲突 3：手机号 AES 加密存储，但短信登录要按手机号查用户

- **需求 §5.3 / §5.4 决策 9 写的是**：手机号/身份证 **AES 加密**存储（密钥放环境变量）。
- **T41 需要**：用户输入手机号 → 找到对应账号。

**AES-CBC 带随机 IV 时，同一手机号每次密文都不同，无法建索引、无法等值查询。** 直接 `WHERE phone_enc = AES(?)` 查不到。

**建议方案：加密列 + 哈希列，各司其职。**

| 列 | 算法 | 用途 | 可否索引 |
|----|------|------|---------|
| `phone_enc` | AES（密钥 `FIELD_ENC_KEY`） | **存储**，解密后用于展示/回填 | ❌ |
| `phone_hash` | HMAC-SHA256（密钥 `PHONE_HASH_KEY`，独立于加密密钥） | **检索**，登录时按手机号定位账号 | ✅ 唯一索引 |

**要点**：
- 两个密钥**必须是不同的值**，且都不进代码库（`.env` / 环境变量）。
- `phone_hash` 加唯一索引，同时天然防止"同一手机号注册两个账号"。
- 这是 T38（数据安全加固）的一部分，**需与 T38 的负责人 D 对齐后再写迁移**，避免两张表用两套加密方案。
- 演示时"直接查数据库 `patient` 表看到密文"这条判据（链路图 §2.10）不受影响——`user.phone_hash` 是 HMAC 不是明文，同样不可逆。

### 3.3 后端设计

#### 3.3.1 接口契约（这两个接口就是要交给 F 整理进接口文档的）

**① 发送验证码**

```
POST /api/auth/sms/send
Auth: 无需登录
Body: { "phone": "13800138000", "scene": "login" | "mfa" }
```

| 返回 | 场景 | 结构 |
|------|------|------|
| 200 | 成功 | `{"code":0,"message":"验证码已发送","data":{"cooldown":60,"mock":true,"masked_phone":"138****8000"}}` |
| 429 | 60s 内重复请求 | `{"code":42901,"message":"请 60 秒后再试","data":{"retry_after":37}}` |
| 429 | 超过当日上限（10 条/号码/天） | `{"code":42902,"message":"今日发送次数已达上限"}` |
| 404 | 手机号未注册 | `{"code":40401,"message":"该手机号未注册"}` |

> ⚠️ **口径提醒**：404 会泄露"某手机号是否注册"。真实产品应对"未注册"返回与成功相同的响应（防枚举）。本项目**演示便利优先**，明确返回未注册；此点在答辩说明中如实标注为"已知差异"。

**② 校验并登录**

```
POST /api/auth/sms/verify
Auth: 无需登录
Body: { "phone": "13800138000", "code": "483920", "scene": "login" | "mfa" }
```

| 返回 | 场景 | 结构 |
|------|------|------|
| 200 | 成功 | `{"code":0,"data":{"token":"<JWT>","user":{...}}}`（`token` 结构复用 T05） |
| 400 | 验证码错误 | `{"code":40001,"message":"验证码错误，还可尝试 3 次","data":{"remain":3}}` |
| 400 | 验证码过期/未发送 | `{"code":40002,"message":"验证码已失效，请重新获取"}` |
| 423 | 连续错误 5 次锁定 | `{"code":42301,"message":"错误次数过多，账号已锁定 10 分钟"}` |

> `scene=mfa` 时，本接口只返回"第二因素校验通过"的凭据，由 T07 的登录页完成后续 JWT 签发——**具体形态由 B 与 T05/T07 的负责人 A、C 在接口契约对齐时敲定，本文档不替 A 决定登录状态机**。

#### 3.3.2 Redis 键设计（与 T06 邮箱验证码共用同一套命名空间）

| Key | 值 | TTL | 作用 |
|-----|----|-----|------|
| `vc:code:{scene}:{target}` | 6 位数字码 | 300s（5 分钟，与 T06 一致） | 验证码本体 |
| `vc:cooldown:{target}` | `1` | 60s | 重发倒计时；`EXISTS` 即拒绝发送 |
| `vc:daily:{target}:{yyyymmdd}` | 计数器 | 当日 24:00 过期 | 每日 10 条上限 |
| `vc:fail:{target}` | 错误次数 | 600s | 累计错误 |
| `vc:lock:{target}` | `1` | 600s | 锁定标记（对齐邮箱 2FA 的"连错 5 次锁 10 分钟"判据） |

> `{target}` 对短信是手机号，对邮箱是邮箱地址——这是把 T06 抽成公用模块的直接收益。**注意：Redis 里存明文手机号属于合规瑕疵**，但本项目 Redis 不对外暴露，答辩说明中列为此项已知简化。

#### 3.3.3 数据模型

```sql
-- 新增表（Alembic 迁移，与需求 §5.3 的 sms_log 定义一致）
CREATE TABLE sms_log (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  channel     VARCHAR(16)  NOT NULL COMMENT 'sms',
  target_enc  VARBINARY(256) NOT NULL COMMENT '收信手机号（AES 密文）',
  target_hash CHAR(64)     NOT NULL COMMENT 'HMAC-SHA256，供检索/去重',
  content     VARCHAR(512) NOT NULL COMMENT '短信正文（含验证码）',
  scene       VARCHAR(16)  NOT NULL COMMENT 'login / mfa / notice',
  message_id  VARCHAR(64)  NULL     COMMENT 'mock-xxxxxxxx / 真实厂商回执 ID',
  result      VARCHAR(16)  NOT NULL COMMENT 'success / fail',
  is_mock     TINYINT(1)   NOT NULL DEFAULT 1,
  sent_at     DATETIME     NOT NULL,
  INDEX idx_target_hash_sent (target_hash, sent_at),
  INDEX idx_scene_sent (scene, sent_at)
) COMMENT='短信发送记录（登录验证码 / 提醒触达共用）';
```

```sql
-- 修改表（配合 §2 冲突 3）
ALTER TABLE user
  ADD COLUMN phone_hash CHAR(64) NULL COMMENT 'HMAC-SHA256(phone)，用于按手机号检索' AFTER phone_enc,
  ADD UNIQUE INDEX uk_user_phone_hash (phone_hash);
```

**`content` 列的注意点**：真实短信正文本身就含验证码，所以落库不算泄密；但**真实接入时建议只落 `message_id` 与模板编号，不落正文**（正文进数据库是审计上的负担）。写代码时用 `settings.SMS_PROVIDER == "mock"` 控制是否写 `content`。

#### 3.3.4 关键流程

```
【发送】
用户填手机号 → 点击「获取验证码」
  │
  ├─ 1. 检查 vc:lock / vc:cooldown / vc:daily  → 命中则按 §3.3.1 返回 429
  ├─ 2. 由 phone_hash 查 user          → 未命中返回 404
  ├─ 3. 生成 6 位随机码（secrets.randbelow，禁止 random.randint）
  ├─ 4. Redis: SET vc:code:login:{phone} = 483920 EX 300
  ├─ 5. SMSProvider.send_code(phone, "483920", scene)   ◄── 唯一被替换的一步
  │        └ MockSMSProvider: logger.info("[MOCK SMS] → %s | %s", phone, code)
  │                            return SendResult(ok=True, provider="mock",
  │                                             message_id="mock-9f3a2c1d", cost_ms=12)
  ├─ 6. INSERT sms_log(... is_mock=1 ...)
  ├─ 7. Redis: SET vc:cooldown:{phone} EX 60 ；INCR vc:daily
  └─ 8. T11 审计中间件自动落 1 条（detail 含明文 code —— 见 §1.3）
  ▼
前端启动 60s 倒计时

【校验】
用户填验证码 → 提交
  │
  ├─ 1. Redis GET vc:code:login:{phone}
  │        ├ 不存在          → 40002「已失效」
  │        ├ 不相等          → INCR vc:fail；≥5 时 SET vc:lock EX 600 → 40001 / 42301
  │        └ 相等            ▼
  ├─ 2. DEL vc:code:... / DEL vc:fail:...
  ├─ 3. 由 phone_hash 查 user → 校验 status=active
  ├─ 4. 签发 JWT（复用 T05 的签发函数，不另写一套）
  └─ 5. T11 审计中间件自动落 1 条「登录成功」
```

**第 1 步的"码不存在"与"码错误"要分开报错**——合并报错会让 60s 重发后的用户看到错误的"错误次数"提示，是常见的体验瑕疵。

#### 3.3.5 Provider 抽象（`app/providers/sms.py`）

```python
class SendResult(BaseModel):
    ok: bool
    provider: str          # "mock" / "aliyun"
    message_id: str
    cost_ms: int
    error: str | None = None

class SMSProvider(Protocol):
    def send_code(self, phone: str, code: str, scene: str) -> SendResult: ...
```

### 4.3 后端设计

#### 4.3.1 接口契约

**① 录入人脸**

```
POST /api/auth/face/enroll
Auth: 需要 Token（本人操作）
Body: multipart/form-data   image=<file: jpg|png, ≤2MB>
```

| 返回 | 场景 | 结构 |
|------|------|------|
| 200 | 成功 | `{"code":0,"message":"人脸录入成功","data":{"face_image_ref":"f_9a3c2e1b","enrolled_at":"2026-09-11T10:22:31"}}` |
| 200 | 覆盖已有录入 | 同上，`message` 为「已更新人脸底图」，`old_ref` 不复用（旧文件异步删除） |
| 400 | 图片为空 / 格式非法 / 超过 2MB | `{"code":40001,"message":"请上传 JPG 或 PNG 格式、2MB 以内的照片"}` |
| 403 | 非本人且非 admin | `{"code":40301,"message":"无权操作他人人脸信息"}` |

> **录入不限次数**，重复录入即覆盖——首次录入与后续更新走同一接口，减少状态分支。

**② 人脸校验（登录）**

```
POST /api/auth/face/verify
Auth: 无需登录
Body: multipart/form-data   username=<str>  image=<file>
```

| 返回 | 场景 | 结构 |
|------|------|------|
| 200 | 通过 | `{"code":0,"data":{"token":"<JWT>","user":{...},"score":0.94,"mock":true}}` |
| 400 | 未录入人脸 | `{"code":40001,"message":"该账号尚未录入人脸，请先用密码登录后录入"}` |
| 401 | 比对不通过 | `{"code":40101,"message":"未匹配到已录入人脸，请调整光线与角度后重试"}` |
| 423 | 连续失败 5 次 | `{"code":42301,"message":"验证失败次数过多，请改用密码登录"}` |
| 404 | 用户名不存在 | `{"code":40401,"message":"用户不存在"}` |

> **报错文案是安全设计的一部分**："未匹配到已录入人脸"比"人脸识别失败"更不容易让演示者误以为是设备问题，也**不要**提示"相似度 12%"这类可被用于试探的信息。

**③ 读取人脸图（受控访问）**

```
GET /api/auth/face/image/{ref}
Auth: 需要 Token —— 仅本人 或 admin
```

| 返回 | 场景 |
|------|------|
| 200 | 返回图片二进制，`Content-Type: image/jpeg` |
| 403 | 他人尝试访问非自己的人脸图 |
| 404 | ref 格式非法（不匹配 `^f_[0-9a-f]{8}$`）或文件不存在 |

> **这是"不可直链"判据的落地方式**：`uploads/private/face/` 整个目录**不注册到 StaticFiles**（见 §2 冲突 2）。验收人拿到 `f_9a3c2e1b` 后拼 `/uploads/face/f_9a3c2e1b.jpg`、`/static/face/...` 各种路径都应该 404。

#### 4.3.2 数据模型

```sql
ALTER TABLE user
  ADD COLUMN face_image_ref  VARCHAR(32) NULL COMMENT '内部标识 f_xxxxxxxx，非路径、非 URL' AFTER phone_hash,
  ADD COLUMN face_enrolled_at DATETIME   NULL COMMENT '最近一次录入时间';
```

**不要**在 `user` 表存磁盘路径、不要存文件扩展名、不要存原始文件名——三者都是"可直链"的来源。

**磁盘布局**

```
uploads/private/face/9a/3c/{uuid4}.jpg     ← 两级散列目录，避免单目录文件数过多
        对外 ref：f_9a3c2e1b（只取 uuid 前 8 位 + 前缀，与目录名无映射关系）
```

> ref 与 uuid 的映射由 `user.face_image_ref` 承载，但**磁盘文件名不等于 ref**，需要一个短映射（`face_asset(ref, disk_path, user_id, created_at)` 小表，或直接用 ref 前 8 位作为文件名——二选一，**建议直接 `{ref}.jpg`**，少一张表，且 ref 本身已是不可枚举的随机值）。此细节由 D 定，写进代码注释即可。

#### 4.3.3 关键流程

```
【录入】
已登录 → 个人设置 / 引导页 →「录入人脸」
  │
  ├─ 1. 前端 getUserMedia({video:{width:640,height:480,facingMode:'user'}})
  │        ├ 浏览器不支持        → 提示"请使用 Chrome/Edge 最新版"
  │        ├ 用户拒绝授权        → 提示"请允许摄像头权限后重试"（含浏览器设置指引）
  │        └ 非 HTTPS 且非 localhost → 提示"摄像头需在 HTTPS 下使用"
  │             （本项目靠 T38 的自签 HTTPS 覆盖；本地 localhost 天然豁免）
  ├─ 2. 实时预览 + 取景框（纯 UI 提示，不接活体检测）
  ├─ 3. 点击「拍照」→ canvas.drawImage(video) → toBlob('image/jpeg', 0.9)
  │        → 冻结画面并展示预览 → 用户选择「重拍」或「确认上传」
  ├─ 4. POST /api/auth/face/enroll (FormData)
  │        ├ 校验 MIME（不信任前端声明的 content-type，用 Pillow 实际解码验证）
  │        ├ 校验大小 ≤ 2MB；Pillow 打开失败即拒绝
  │        ├ FaceAuthProvider.enroll(user, image)      ◄── 外部能力边界
  │        │     └ MockFaceAuthProvider: 写 uploads/private/face/...
  │        │        返回 ref
  │        ├ user.face_image_ref = ref；face_enrolled_at = now()
  │        ├ 若有旧 ref → 删旧文件（失败只记日志，不回滚主流程）
  │        └ T11 审计自动落 1 条 + 字段变更明细（old_ref → new_ref）
  └─ 5. 前端释放 MediaStream（video.srcObject.getTracks().forEach(t => t.stop())）
          ⚠️ 不释放会导致摄像头指示灯常亮 —— 演示时非常明显

【校验】
登出 → 登录页 →「人脸识别」→ 输入用户名 → 打开摄像头 → 拍照 → 提交
  │
  ├─ 1. 校验失败次数（复用 vc:fail / vc:lock 同一套 Redis 键，target = username）
  ├─ 2. 查 user；face_image_ref 为空 → 400「尚未录入人脸」
  ├─ 3. FaceAuthProvider.verify(user, image)           ◄── 外部能力边界
  │        └ MockFaceAuthProvider（**采用 §2 冲突 1 的方案 A**）：
  │             ① 底图不存在 → passed=False
  │             ② 请求图为空 / 解码失败 → passed=False
  │             ③ dHash(请求图) 与 dHash(底图) 的汉明距离 ≤ 20 → passed=True
  │             score = 1 - distance/64
  ├─ 4. passed → 签发 JWT；失败 → INCR 失败计数
  └─ 5. T11 审计自动落 1 条（**detail 中不含图片与任何路径，只记 ref 与 score**）
```

#### 4.3.4 Provider 抽象（`app/providers/face.py`）

```python
class EnrollResult(BaseModel):
    ok: bool
    ref: str | None = None
    provider: str = "mock"
    error: str | None = None

class VerifyResult(BaseModel):
    passed: bool
    score: float = 0.0
    provider: str = "mock"
    reason: str | None = None

class FaceAuthProvider(Protocol):
    def enroll(self, user_id: int, image_bytes: bytes) -> EnrollResult: ...
    def verify(self, user_id: int, image_bytes: bytes) -> VerifyResult: ...

class MockFaceAuthProvider:
    """模拟实现：不做活体检测，但真实执行一次图像特征比对（感知哈希）。
    接入腾讯云人脸核身时新增 TencentFaceAuthProvider 实现同一 Protocol。"""
    HAMMING_THRESHOLD = 20      # 64 位 dHash，见 §2 冲突 1

    def verify(self, user_id, image_bytes) -> VerifyResult:
        ref = self._repo.get_ref(user_id)
        if not ref:
            return VerifyResult(passed=False, reason="NOT_ENROLLED")
        if not image_bytes:
            return VerifyResult(passed=False, reason="EMPTY_IMAGE")
        d = _dhash_bytes(image_bytes).hamming(_dhash_file(self._repo.path_of(ref)))
        return VerifyResult(passed=d <= self.HAMMING_THRESHOLD,
                            score=round(1 - d / 64, 4),
                            provider="mock")
```

**`enroll()` / `verify()` 只接收 `bytes` 与 `user_id`，不接收 Flask/FastAPI 的请求对象**——这是保证"换 Provider 时上层零改动"的关键。真实 Provider 需要的额外参数（如腾讯云的证件号）从 `settings` 读，不从这里传。

## 6. 答辩口径与演示脚本

### 6.1 统一答辩口径（照念即可）

> 「短信与人脸在当前版本中是**模拟实现**。我们没有把功能做成假的——登录页、倒计时、失败锁定、权限校验、图片存储、审计留痕全部走真实链路，被替换的**只有向外部服务发起的那一次网络请求**。代码上是 `SMSProvider` 与 `FaceAuthProvider` 两个抽象接口加 Mock 实现，接入阿里云短信或腾讯云人脸核身时，只需要新增一个实现类、改 `.env` 一个开关，业务代码和前端页面一行都不用动。」

**接着当场打开 `app/providers/sms.py` 展示接口定义**——排期 §3.5 明确要求"主动说明而非掩盖"，这是设计能力的体现。

**必须主动交代的三个局限**（主动说是加分，被问出来是减分）：

1. 人脸未接活体检测，用照片即可通过；
2. 验证码明文落在审计 `detail` 中仅为演示便利，真实环境必须脱敏；
3. 人脸未做合规告知与单独授权流程，属二期合规项。

### 6.2 演示脚本片段

**① 短信登录闭环（约 90 秒）**

```
1. 打开登录页 → 切到「短信验证码登录」→ 指向「模拟环境」角标，口头说明这是模拟实现
2. 输入 138****8000 → 点「获取验证码」→ 按钮变 60s 倒计时
3. 立刻再点一次 → 按钮已禁用（口头："服务端也有 60s 冷却，刷新页面也绕不过"）
4. 切到 admin 账号的审计页 → 按时间倒序 → 找到 POST /api/auth/sms/send
   → 展开 detail → 念出明文验证码  ← ⭐ 全场最有说服力的一步
5. 回登录页输入验证码 → 登录成功进入工作台
6. （可选）故意输错 5 次 → 展示锁定提示
```

**② 人脸识别闭环（约 90 秒）**

```
1. 用密码登录 → 进入人脸录入页 → 开启摄像头（现场真拍，不预录）
2. 拍照 → 预览 → 故意点「重拍」→ 再拍一次 → 确认上传
3. 打开浏览器开发者工具 Network → 展示上传请求
4. 拿到返回的 ref（如 f_9a3c2e1b）→ 在地址栏直接拼 /uploads/face/f_9a3c2e1b.jpg
   → 404  ← ⭐ 口头："人脸是敏感生物信息，不存在可猜测的静态 URL"
5. 退出登录 → 人脸识别入口 → 本人校验 → 通过
6. 换另一位医生的照片 → 校验失败  ← ⭐ 判据⑤
7. 查审计页 → 人脸录入记录（含 ref 标识，无路径）
```

> **演示前置检查（演示当天早上必做）**：摄像头权限已授权、光线充足、演示账号的人脸底图是**当天**采集的（避免角度/光线差异导致 dHash 误拒）、HTTPS 证书有效。
