### 5.2 三条对不上的（`M0-05` 契约校验将来必须拦住的就是这些）

| 路径 | 问题 |
|------|------|
| `/api/allergies/{allergy_id}` | **参数名与契约不一致**。契约（`openapi.yaml:822`）写的是 `/api/allergies/{id}`。按路径字符串严格比对，这是一条"多出来的接口 + 一条没实现的接口"，两条误报 |

### 5.3 健康检查的真实行为（三处口径不一致，务必分清）

| 路由 | 行为 |
|------|------|
| `GET /health` 与 `GET /api/health` | **恒 200**。依赖 down 只写在 body 里：`{"db": "ok"\|"down"\|"disabled", "redis": ...}`。键名是 **`db`**，不是 `database`（`main.py:236-254`，理由写在 `:239-241`：`auth_schemas.py` 由契约生成） |
| `GET /api/health/live` | 恒 200，普通信封（`main.py:269-271`） |
| `GET /api/health/ready` | **依赖 down 时返回 503**：`available = "down" not in checks.values()`，`status_code=200 if available else 503`（`main.py:289-291`）。响应体还额外带顶层 `status` 与 `checks`，其中 `checks` 与 `data` 内容重复——**这不是纯信封** |

**因此"健康检查永不出 5xx"这句话只对前两条成立。** 全站确实存在 503：`/api/health/ready`、`RedisError`（`main.py:230-234`）、`SQLAlchemyError`（`main.py:256-261`）、以及 `JWT_SECRET` 未配置（`backend/tests/test_security.py::test_unconfigured_jwt_secret_fails_closed` 断言了 503）。任何声称"本 API 没有 503"的文档都是错的。

### 5.4 契约里没有实现的 60 条，按模块归属

`/api/users*`、`/api/roles`（M1-07）；`/api/patients/{no}/histories*`、`/api/histories/{id}`、`/api/patient-groups*`（M2）；`/api/emr/*`、`/api/drugs`（M4，15 条）；`/api/consultations*`、`/api/uploads/images`、`/ws/chat/{room_id}`（M3）；`/api/meetings*`、`/api/materials/{id}/download`（M5）；`/api/health-plans*`、`/api/patients/{no}/vitals*`、`/api/reminder*`、`/api/assessments/{id}`（M6）；`/api/audit-logs*`（M8）。

**结论**：契约写得比实现早得多，它描述的是目标态。**不要拿契约当"已实现"的证据。**

## 8. 模拟、死代码与已知缺口

### 8.1 🔴 人脸登录是模拟（最高优先级红线）

- `backend/app/face_login.py:18-21` 的 `match_face()` **恒返回 `True`**，源码自述 `# Demo only: every matching attempt succeeds until matching is implemented.`，其上一行是 `# TODO: Implement face matching against the user's enrolled reference image.`
- 该路由在匿名白名单里（`security.py:25-38`；`security.py:20-24` 有 WARNING 注释）。
- **净效果：任意合法 JPEG + 任一存在的活跃用户名 = 一个真实的 2 小时 token。**
- 契约 `openapi.yaml:92` 的描述是诚实的（"Demo matcher always returns true"），README 的说明也诚实。
- **要求**：页面可见角标、响应体 `"mock": true`、答辩口径三处一致标注为模拟；**绝不可对外部署**。

### 8.2 已移除但仍有痕迹的 passkey

`models.py:127` 的 `Passkey` 表与迁移 `e3b6c9d24f75` 都还在，但**全仓库没有任何代码读写它**（除模型定义与迁移本身）。端点已删除。README 说明是"为迁移兼容保留"。**它是一张死表**——留着不影响功能，但会让人误以为有 passkey 能力。
