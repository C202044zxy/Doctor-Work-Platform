## 页面与架构

- `/consultations` 是双标签容器：`PatientConsultationView.vue` 承载 M3，`RemoteConsultationView.vue` 承载 M5。`?room=<id>` 保留问诊链接；`?tab=remote` 打开会诊。切换标签卸载子页面，释放聊天连接和媒体设备。两个子页面共用 `frontend/src/components/RoomPanel.vue` 与房间键模块 `frontend/src/room.js`：同一条 `WS /ws/chat/{room_id}`，问诊用裸数字、会诊用 `m<id>`。
- 侧栏只保留 **Consultations**。在 Patient consultation 内点 **Search consultation records** 查询记录与导出（`/consultations?view=records`）；旧 `/consultation-records` 自动重定向；`/remote-consultation` 重定向到会诊标签。
- `/patients/:patientNo` 承载患者详情、M5 会诊记录、M2-06 病史时间线、M6 Health data。健康管理不另增主侧栏入口。警示条、分组、病史时间线**共用同一次** `GET /api/patients/{patient_no}`（服务端一个 reader 同时喂列表接口和详情响应，排序不会有两份），任一写操作后重读它。
- `/patients` 的 `Manage groups` 是 M2-05 的唯一写入口，在分组筛选旁。契约没有成员名单接口，因此对话框只显示 `member_count` 并写明去哪查名单。
- `/records`、`/review`、`/my-submissions` 使用 main 的 M4 接口；Dashboard 和外壳使用 main 的 M6 未读字段 `unread`。
- 后端 `main.py` 统一装配认证、患者/分组、M3、M4、M5、M6、短信与审计。`chat.py` / `calls.py` 保存活动连接与信令状态，SQLite 保存消息和已结束通话；开发/当前部署使用单 API worker。
- 浏览器媒体通过 WebRTC 传输；WebSocket 用于信令与图文。视频提供摄像头+麦克风、仅麦克风、仅接收模式；仅接收不访问设备。
- 同一 APScheduler 注册授权过期、main 健康提醒、兼容提醒（独立 job ID）；两套提醒表和未读统计互不混用。
- 审计页的**动作下拉改读服务端**（`GET /api/audit-logs/actions`，admin 专属，返回 `audit.MARKED` 与 `audit.ACTIONS` 的并集）。原先它是 `AuditLogView.vue` 里手工抄的数组，已漂移：T17 的五个 `patient_group.*` 与 `temp_grant.expire` 都不在名单里，于是「按动作审阅」对这些条目失效。该接口不是查询审计日志的前提——`action` 是精确匹配字符串，手输同样有效；它只是让新增动作在一处登记即可被筛到。

## 种子数据（2026-09-21 新增第三层）

种子分三层，每层依赖上一层：`backend/app/seed.py`（角色 / 科室主数据）→ `backend/app/seed_demo.py`（4 个账号 / 3 个患者 / 过敏与病史，§4 基线）→ **`backend/app/seed_flow.py`（全流程临床状态）**。第三层落库：3 条问诊（waiting / active / ended，共 55 条消息、1 张图片、1 通 60 秒通话）、3 条病历（draft / pending / archived，6 个版本快照）与 3 条医嘱（passed / warning / stopped）、1 场已完成会诊（1 份资料 + 1 份 3 条专家意见的报告 + 1 条**已过期**授权）、1 份健康方案 + 3 条提醒规则 + 3 条提醒日志（1 条未读）+ 30 条体征 + 1 份评估，并在 `uploads/` 写出 2 个真实可读的附件（1 页 PDF 与 1 张 PNG）。

它**不写 `audit_logs`**（审计只记录真实发生过的事，两次运行查询结果应能解释每一次操作）、**不新建账号或患者**（`scripts/build_db.py` 对账号与患者的校验在它之后仍然成立）。医嘱的 `validation_status` / `validation_detail` 与体征的 `is_abnormal` 由运行时函数 `app.emr_validation.validate_orders`、`app.health._is_abnormal` 现场计算，不抄常量——否则同一读数会在图表与接口里得到两种结论。

`scripts/build_db.py` 默认执行三层并校验行数与附件；`--no-flow` 跳过第三层（要空工作台时用），`--no-demo` 只留主数据。启动脚本 `backend/start.sh` / `start.ps1` 仍只跑前两层，因此开发模式要全流程数据需手动 `uv run python -m app.seed_flow`。测试见 `backend/tests/test_seed_flow.py`（17 条，含幂等、附件重写、已过期授权、本月筛选、阈值一致性、“演示自己建的会话不被注入”，以及计数与实际写入行数一致、状态缺失能被发现）。`--check` 不只看行数：它还按状态名检查 waiting / active / ended 与 draft / pending / archived，因为别人占住槽位时行数可以是够的，而审阅队列或待接诊队列其实是空的。

## 数据库与兼容边界

当前唯一 Alembic head：`e2b7d4c1a905`（M5 房间复用：`room_key`），上一步是 `d5e8a3b71c04`（M2-06 `patient_history`），父链再上一步是合并原分支 `c93f105d2e71` 与 main `a7f3c2e91d04` 的 `e6a31c29d408`。共 19 个 revision。空库包含 **37 张表**（含 alembic_version）和 2 个审计只追加触发器——本次**不新建表**，`EXPECTED_TABLES` 因此未变，但 `scripts/build_db.py` 仍实跑通过以证明模型与迁移一致。

`e2b7d4c1a905` 把 `consult_message` / `call_log` / `image_upload` 的 `consultation_id` 换成 `room_key`（字符串：问诊是裸数字、会诊是 `m<id>`），幂等唯一键从 `(consultation_id, sender_id, client_id)` 迁到 `(room_key, sender_id, client_id)`；旧行按 `consultation_id` 回填，`consultation_id` 降为可空。SQLite 走 `batch_alter_table(recreate="always")`，downgrade 会删除只属于会诊的行（迁移里已写明）。

`patient_history` 的排序键是 `onset_date`，而它可空。reader 用 `onset_date IS NULL`、`onset_date DESC`、`id DESC` 三段排序：**不用 `NULLS LAST`**——schema 是双方言，`pymysql` 是硬依赖，而 MySQL 8 没有这个语法；`IS NULL` 在 SQLite/MySQL 上都渲染成 0/1。

两边原先都创建 `medical_order`，直接合并会在第二次建表时报错。现在 main M4 使用 `medical_order`；旧分支医嘱完整保留在 `legacy_medical_order`。旧 `health_plan` / `reminder_rule` / `reminder_log` 与 main 的复数表名并存。

为使碰撞发生前即可分流，对 `bd9e76dbea39` 与 `7ad4cb527bd2` 两个历史 revision 添加了表存在判断/改名兼容逻辑，revision ID 和父链不变；新增 merge revision 汇合两条分支。不能仅在 merge revision 末尾改名，因为重复建表会更早失败。空库、从两边已发布 head 升级、带医嘱数据升级、downgrade 到 base 均有验证。

正式路径 `/api/emr/orders`、`/api/health-plans`、`/api/reminder-rules`、`/api/reminders` 使用 main 实现。旧接口全部加 `/api/legacy` 前缀，契约位于 `api/legacy.openapi.json`（由主契约引用）。旧健康页面在 `/legacy/health-plans`、`/legacy/reminders`；旧医嘱仍依赖原适配器，缺失返回 503，正式医嘱请使用 M4 页面。

旧医嘱不自动复制为 M4 医嘱：两套 record_id 语义不同，直接迁入会形成错误病历关联。兼容表保留原数据，不代表完成业务数据转换。

## 健康检查与模拟范围

`/health` 和 `/api/health` 是同一响应，依赖故障仍返回 200；`/api/health/live` 只检查进程；`/api/health/ready` 要求数据库与 Redis 都为 ok，否则 503。登录、验证码和注销依赖 Redis，进程启动成功不代表认证可用。

短信仅在 `APP_ENV=dev` 开放。发送接口不返回验证码，受限 preview 才能读取，成功验证签发真实 JWT；号码未绑定真实手机，不构成真实短信二次认证。人脸登录也是模拟，两者不能对外宣称真实身份核验。

## 开发端口自动回收（2026-09-21）

启动脚本的端口预检由「占用即退出」改为「可确证是本项目遗留才回收」。判定与回收都在共用的 `backend/app/dev_runtime.py`（`reclaim` 子命令），`backend/start.ps1` 与 `backend/start.sh` 各改一个词，调用方式一致。

判定规则（纯函数 `classify_holder`，安全策略只此一处）：API 侧要求镜像名为 `python` / `uvicorn` 且命令行含 `uvicorn` 与 ASGI 目标 `app.main:app`，用带词边界的正则匹配以免 `some_other_app.main:app` 以子串命中；前端侧要求镜像名为 `node` 且命令行同时含 `node_modules`、`vite/bin/vite.js`、`--port 5173`、`--strictPort` 四个独立信号。判定未通过时**一个都不停**，打印占用者 PID、进程名、命令行后退出 1——原先「不连到旧 API」的安全阀对无法确证归属的占用者原样保留。`--dry-run` 可在不执行的前提下审计该策略；端口空闲时整条路径零副作用，CI 的 Windows 任务因此不受影响。

已实测：现场孤儿（PID 14900）被 `--dry-run` 精确指认、被 `reclaim` 停止，5173 释放且重复执行为静默 no-op；以同一条 Vite 启动路径但不带 `--strictPort` 占住 5173 时，`reclaim` 拒绝并退出 1，进程存活。

残余歧义（无法归零）：另一个项目若恰好也以 `node_modules/vite/bin/vite.js --port 5173 --strictPort` 启动，与本项目形态无法区分，会被误杀。已知边界：手工直接启动、未带 `--strictPort` 的本项目 Vite 无法被识别，需人工停止；脚本自身启动的实例始终带该参数。

同批修复 `backend/start.sh` 的清理只杀一层的问题（`$!` 是 exec 进 `uv run` 的 subshell，`uv run` 若 fork 而非 exec 出 Uvicorn 就会留下孤儿），改为递归 `kill_tree`。

## 视频通话本机回环（2026-09-21）

`/consultations` 的视频面板在 **Start video call** 旁新增 **Test on this computer (loopback)**。它跳过「对方是否在线」的检查——该检查在服务端 `calls.py`，只数同房间内除自己以外的连接，没有别人就拒绝 offer——改为在**同一个页面内**把两个 `RTCPeerConnection` 用内存对连（`frontend/src/call-loopback.js`），把自己的摄像头接回自己。单机因此不必再开两个浏览器抢同一台摄像头，就能看到真实画面。

它的形状必须写清楚：**不发 offer、不置 `call_id`**，所以不产生 `call_log` 行，也不产生审计条目——没有通话发生，只有一段真实的本地媒体链路；面板文字与状态行都直接写出这一点。回环侧音频在页面上静音以免啸叫；`Receive only` 模式下没有媒体源，按钮不可用。

自动化：`frontend/tests/call-loopback.test.js` 7 条（假 `RTCPeerConnection`，断言对连驱动顺序、远端描述落地前的 ICE 候选必须缓存而非丢弃、远端轨道收集、连接真正建立后才 resolve、失败时两端口都关闭、无 WebRTC 时拒绝而不是半启动）。前端全套 **62 passed**，生产构建通过。手测步骤见《视频通话同机测试与排错》。

上一节「合并验证与复核」记的前端 **52 passed** 与本次实测的 62（其中 7 条为本次新增，即改动前为 55）不符，差额来源未查明；以本次实测为准。
