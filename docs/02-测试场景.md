**三条硬规矩**

1. **场景逐条实跑**，不以"接口返回 200"代替期望结果；每条必须能指出**期望中的具体值**（字段名、状态码、条数）。
2. **模拟模块的判定必须带"模拟"标注检查**（§5），标注缺失即判该场景不通过。
3. **零代码模块的场景一律标 `未开始`**，不得因为"设计上没问题"而预先标记通过。

## 6. 答辩口径：可能被问到的尖锐问题

> 原则：**能承认的一律承认，能给出边界的一律给边界，不确定的说不确定。** 被问倒一次比被查出一次好。

**Q1：契约里有 77 条路径，你们实际实现了多少？**
答：**77 条里只有 18 条在代码里存在**（截至 2026-09-14）。实现的 18 条集中在认证（`/api/auth/login`、`/send-code`、`/verify-code`、`/logout`、`/api/me`、`/api/auth/signup(+verify)`、`/api/auth/face/login`）、临时授权（`/api/temp-grants`）、患者与过敏（`/api/patients`、`/api/patients/{patient_no}`、`/api/patients/{patient_no}/allergies`、`/api/allergies/{id}`、`/api/allergens`）、科室字典与健康检查（`/api/departments`、`/health`、`/api/health`）。此段统计是 2026-09-14 的历史核对结果；**M5 已于 2026-09-17、M4 已于 2026-09-19 落地**，当前现状见 `docs/03-实现现状.md`。 契约是目标态，不是现状；我们把差距写进了文档而不是抹平。此外 CI 里目前**没有契约校验步骤**，这一点我们也不掩饰——它是 M0-05，优先级排在功能性任务之后。

**Q2：人脸识别是真的吗？**
答：**不是。** `match_face()` 恒返回 `True`，只要用户名存在、账号可用就通过，**不做任何生物特征比对**。真实的部分是：摄像头采集、图片 SHA-256 指纹的存取、不落原图的隐私约束、登录限流。我们把它放在独立编号 S2 并标注为模拟，就是为了不让人误以为是真能力；接真实服务时只需替换 `FaceProvider` 实现。

**Q3：短信验证码真的发出去了吗？**
答：**没有出网，也没有接运营商。** 短信渠道是 S1 模拟：验证码本身是真实的（Redis 签发、TTL、一次性、与邮箱共用同一限流计数器），但"发送"只是写入本地 `notify_outbox`，演示时通过"模拟手机"浮层查看。**S1 目前是未开始状态，登录页当前只有邮箱和人脸两条渠道**——这一条我们按未完成记，不写成已完成。

**Q4：通话录像能回放，是真的录下来了吗？**
答：**没有任何音视频文件。** S3 回放的是通话**事件时间线**（呼叫 / 接通 / 心跳 / 挂断），由 WebSocket 信令加每 5 秒心跳重建，页面顶部固定标注 "SIMULATED PLAYBACK — NO AUDIO OR VIDEO"。真实部分只有 `call_log` 的起止与时长。

**Q5：既然是 15 个工作日，为什么有模块没做完？**
答：剩余任务量约 323h（主模块 195h + 模拟 54h + 文档 50h + 联调 24h），15 天 × 6 人 × 4h 扣掉会议与返工后可用约 290h，**任务量本身就大于产能**。所以我们预先定了降级顺序 **S6 → S5 → S3 → S4**，并在文档里写明砍掉每一层要付出什么代价。这不是意外，是排期时就承认的取舍。

**Q6：为什么把数据库从 MySQL 换成 SQLite？**
答：课程项目没有 DBA 与运维成本预算，SQLite 单文件随 `backend/` 一起交付、零外部依赖，新机器一条命令就能起。**Redis 保留不变，而且是认证硬依赖**（登录票据、验证码、JWT 黑名单、登录限流四件事都放在 Redis 里）；Redis 挂了只影响登录链路，其余接口按 M0-03 口径仍返回 200 并标 `redis:"down"`。`compose.yaml` 与 CI 已同步为 SQLite + Redis（compose 中无数据库容器、使用 `sqlite_data` 卷并设置 `DATABASE_URL: sqlite:////data/doctor.db`，CI 的数据库校验步骤已改名为 "Verify real SQLite and Redis security behavior"）。

**Q7：医生社区为什么不做？**
答：老师原始需求里它标注为 Optional，且与核心诊疗流程相对独立，工作量约等于整个问诊模块。为保证核心模块质量，整体列为二期；二期设计要点（手动脱敏后发布、与患者库物理隔离、模块可整体关闭）已保留在文档里。

**Q8：前端之前那些页面看起来都是做好的，是假的吗？**
答：合并 M4 与 M6 后，View 和外壳已无 `demo-data.js` 直接导入；M4、M5、M6 与工作台使用真实接口。M3 患者问诊仍为未实现空态，不可描述为已实现。

**Q9：跨科室访问返回 404 而不是 403，是不是掩盖了 bug？**
答：不是。**403 会泄露"该患者存在"这一事实**，所以跨科室数据一律返回 404，角色权限不足才返回 403。这两套口径在 M1 里是硬性要求，并且有自动化断言（15 组合越权矩阵）。

**Q10：`/metrics` 为什么不遵守你们自己的响应封装规范？**
答：因为 Prometheus 文本格式本身就是接口契约的一部分，包成 `{code,message,data}` 就没法被 `promtool` 与真实 Prometheus 解析。这是**全项目唯一一个例外**，并在 `openapi.yaml` 的描述字段里显式写明。它的暴露范围默认限制在本机回环 + 可配开关，不公开暴露。

**Q11：模拟模块的验证码写进了 `notify_outbox`，和"验证码绝不出现在响应体与日志"冲突吗？**
答：冲突，我们承认这是**已登记的契约例外**。处置是：验证码列只在 `APP_ENV=dev` 下写入，生产 / 演示正式环境该列为空；`GET /api/notify-outbox` 仅 admin 可访问，登录页浮层只返回**当前 ticket 关联的那一条**，不回表。

**Q12：15 天里如果 S1 / S2 也被砍了呢？**
答：那是最坏情况，代价最大——它们成本最低（合计 14h）却最容易被追问"你到底砍了什么"。我们的立场是：**S1 / S2 不进入降级顺序**，宁可先砍 S6 / S5 / S3 / S4。

**Q13：怎么证明你们说的状态是真的？**
答：每个模块的状态都有对应的代码证据或"零代码"结论，写在《01-任务安排.md》§3 的"现状（代码事实）"里；每条测试场景要么给出可复现的期望值，要么明确标 `未开始`。**凡是没跑过场景的模块，状态最多是 `部分完成`，不存在"代码写完即完成"。**

**Q14：演示时如果现场挂了一个模块怎么办？**
答：三条流程按模块解耦，流程 1 只依赖 M1 / M2 / M3 / M4，流程 2 依赖 M1 / M3 / M5，流程 3 依赖 M1 / M6 / S1 / S4。**任一模拟模块（S1 / S3 / S4 / S5 / S6）缺失都有替代口径**（见 §3 各流程下的降级说明），核心业务链条不依赖任何模拟模块。
