# 视频通话：同一台电脑测试与排错

## 为什么会 device in use / timeout

原先两端都强制同时申请摄像头和麦克风。同一台电脑的两个浏览器可能争用一个硬件设备，浏览器会报 NotReadableError / Device in use。该错误也可能来自设备驱动，不能仅凭错误断言是哪一个进程占用。

另一个已修复的问题是原先从拨号到接通共用 25 秒期限，等待接听和设备授权会挤占连接时间。现在等待接听为 60 秒；点击 Answer 后通过 call_accept 开启独立 45 秒设备准备期限；发送 call_answer 后再给 45 秒建立连接。重复 accept/answer 不能延长期限。

## 同机手测步骤（推荐）

1. 在 D 盘原仓库启动开发服务，打开两个独立浏览器（例如 Chrome 与 Edge），分别登录 dr_wang 与 dr_li。不要使用共享 localStorage 的两个普通标签页。
2. 发起并接诊同一个问诊，双方打开同一房间，确认 active / Connected。
3. A 的 **Local media** 选择 **Camera and microphone**。关闭其他正在使用摄像头的应用或人脸预览页面。
4. B 的 **Local media** 选择 **Receive only (no devices)**。B 完全不打开摄像头/麦克风，也不弹硬件授权。
5. A 点 **Start video call**，B 在 60 秒内点 **Answer**。双方应显示 Video: connected，B 能看到并听到 A。A 看不到 B 的画面是预期行为，因为 B 没有发送媒体。
6. 挂断，交换两端模式，再次拨号：A 选 Receive only，B 选 Camera and microphone。这次 A 应看到/听到 B。
7. 挂断后确认摄像头指示灯熄灭（若其他程序仍占用则不会熄灭），重新拨号应能重新获取设备。

这属于真实 WebRTC 的单向媒体测试，不是假画面，也不等于双向摄像头验收。两端都选 Receive only 时没有任何音视频源，不应期待画面。要验收双方同时开摄像头，请使用两台有独立摄像头的设备，或支持多客户端共享的设备。

Microphone only 只申请麦克风，不申请摄像头；如果麦克风也被独占，仍应改为 Receive only。同机测试戴耳机避免反馈啸叫。

## 错误对应处理

- **Camera or microphone could not be opened**：可能是设备占用或驱动问题。关闭摄像头应用、其他视频页/人脸页，或将这一端改为 Receive only 后重新拨号。不会悄悄替你降级。
- **permission was denied**：在浏览器站点设置允许摄像头/麦克风，或使用 Receive only。
- **No answer within 60 seconds**：确认另一账号已打开同一房间并点击 Answer。
- **Media connection timed out**：已进入接听/媒体连接阶段。检查设备授权、浏览器控制台、网络和防火墙；先按本页同机单向方案验证。
- 修改了后端代码触发 reload 会终止当前通话，刷新双方页面后重拨。

当前仍使用直连 WebRTC（无 STUN/TURN）。本机使用 localhost / 127.0.0.1；不同电脑访问局域网普通 HTTP 时可能不能使用摄像头，必须配置可信 HTTPS。公网/NAT 环境仍需 TURN，延长超时不能解决不可达网络。

## 自动化覆盖的边界

Node 单元测试覆盖 receive-only 不申请设备、音频模式约束和轨道释放。后端测试覆盖分阶段期限、错误角色与重复信令。浏览器集成测试使用合成媒体验证真实 WebRTC 连接与轨道释放，不代表物理摄像头共享能力已经通过验收。


可选复验（已安装 Playwright 与 Edge）：开发服务运行时，在仓库根执行 `node scripts/verify_video_modes.cjs`；可用 PLAYWRIGHT_MODULE_PATH 指向已有 Playwright。脚本使用独立浏览器上下文、演示账号与合成设备，不占用实际摄像头。结束后注销测试会话；不要把测试通过等同于物理设备验证通过。

参考：[MDN getUserMedia 错误说明](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)。NotReadableError 还可能由操作系统、浏览器或硬件故障触发，不能只凭错误定位占用者。
