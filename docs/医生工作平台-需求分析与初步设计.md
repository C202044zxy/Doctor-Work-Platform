## 1. 项目概述

### 1.1 项目背景

医生的日常工作——登录系统、查阅患者资料、线上问诊、书写病历、远程会诊、随访管理——分散在多个孤立系统中，造成数据孤岛、重复录入与安全隐患。本项目构建一个**一体化的医生工作平台**（B/S 架构 Web 系统），覆盖"登录 → 患者管理 → 问诊 → 病历 → 会诊 → 随访"流程，同时满足医疗行业对**安全、合规、可审计**的基本要求。

### 1.2 项目目标（按课程作业定位）

- **跑通完整业务闭环**：一个医生从登录到完成一次"检索患者 → 图文问诊 → 写病历 → 提交审阅 → 上级批准"的全流程演示。
- **安全合规有体现**：多因素登录、角色权限、临时授权、全程审计日志——这是本项目的**亮点与评分点**，优先保证完成度。
- **体验合格**：界面整洁统一（Element Plus 组件库），常规操作无明显卡顿。

### 1.3 需求全景（源自 PPT 的 9 大模块 + 裁剪结论）

| # | 模块 | 裁剪结论 | 说明 |
|---|------|---------|------|
| 1 | 安全账户登录 | **简化实现** | 保留：密码 + 邮箱验证码双因素、三级角色权限、临时授权、按科室的数据范围。砍掉：人脸识别 |
| 2 | 患者信息管理 | **完整实现** | 多条件搜索、档案查看编辑、手动分组。工作量适中，是全平台数据核心 |
| 3 | 在线问诊 | **图文为主，视频为加分项** | 图文聊天（WebSocket）为核心；视频用腾讯云 TRTC Web Demo 集成；砍掉自动录像 |
| 4 | 电子病历 EMR | **完整实现（核心亮点）** | 模板、医嘱校验、上级审阅归档，是业务深度所在 |
| 5 | 远程会诊 | **简化实现** | 复用聊天室能力：发起/接受、资料共享（文件上传）、报告生成（模板渲染）。多人视频为加分项 |
| 6 | 患者健康管理 | **简化实现** | 手动录入体征 + ECharts 趋势图 + 站内定时提醒 + 简单评估表。砍掉 IoT 设备接入、短信/微信触达 |
| 7 | 医生协作社交 | **本期不做** | PPT 已标注 Optional；在文档中保留设计思路，答辩时说明"因工作量取舍，列为二期" |
| 8 | 操作日志与审计 | **简化实现（必做）** | 中间件自动记日志、日志查询页、CSV 导出。系统监控简化为管理端统计面板 |
| 9 | 用户体验（非功能） | **作为约束贯穿** | 前后端分离、分页查询、HTTPS/加密、数据不丢 |

## 2. 范围裁剪决策

> 原则：**砍掉一切"花钱、要硬件、要第三方资质"的东西，简化一切"企业级"的东西，保留一切"答辩时能演示出系统设计能力"的东西。**

### 2.1 明确不做的（写进答辩说明即可）

| 砍掉项 | 原因 | 替代/说辞 |
|--------|------|----------|
| 人脸识别登录 | 需要活体检测服务，课程项目无法落地 | 双因素改为"密码 + 邮箱验证码"，答辩时说明"生物认证预留接口" |
| 短信验证码 | 短信服务要企业资质、要花钱 | 用邮箱验证码（QQ/163 邮箱 SMTP 免费开通），Redis 存 5 分钟有效 |
| 问诊自动录像 | 云端录制是 TRTC/Agora 付费功能 | 砍掉。答辩时用系统录屏演示视频通话；"会话记录管理"以图文记录 + 通话元数据（时长、时间）代替 |
| IoT 设备体征采集 | 没有硬件 | 医生/演示账号手动录入 + 写一个脚本造模拟数据流 |
| 短信/微信提醒触达 | 同短信原因 | 站内通知（提醒列表 + 工作台红点） |
| 医生社区（模块 7） | PPT 标注 Optional，工作量 ≈ 一个小型论坛 | 完全不做，文档保留设计 |
| 动态权限配置界面 | 企业级 RBAC 管理后台工作量大 | 权限矩阵**写死在代码/配置中**（3 个角色），管理员只管"用户-角色分配 + 临时授权" |
| 微服务 / 消息队列 / MinIO | 课程项目用不上 | FastAPI 模块化单体；本地磁盘存上传文件；APScheduler 做定时任务 |

### 2.2 保留并要做好的（评分核心）

1. **双因素登录 + 三级角色 + 临时授权 + 科室数据范围**——权限体系是本系统区别于普通 CRUD 项目的地方。
2. **EMR 全流程**：模板书写 → 医嘱校验（过敏冲突、剂量范围）→ 提交 → 上级审阅 → 归档只读。
3. **审计日志**：FastAPI 中间件统一埋点，日志表只插不改，可按用户/时间/操作类型查询并导出 CSV。
4. **图文问诊（WebSocket）**：实时聊天 + 图片发送 + 历史记录检索。
5. **健康趋势图表**：ECharts 折线图 + 异常值标红——演示效果好、工作量可控。

## 3. 需求分析

### 3.1 模块一：安全账户登录（简化实现）

**需求要点（PPT）**：多因素认证、角色权限、临时权限、数据范围控制。

**分析理解**
- 这是全平台安全基石，其余模块的访问控制都依赖它。
- 权限分两层：**功能权限**（能用哪些功能，由角色决定）+ **数据权限**（能看哪些患者，由科室归属决定）。
- 临时权限是亮点：会诊场景下把某患者数据临时开放给外院/外科室医生，到期自动回收——需要"带过期时间的授权表"。

**落地设计（本组水平）**
1. 登录流程：账号密码 → 邮箱验证码（Redis 存 5 分钟）→ 签发 JWT。
2. **3 个固定角色**（权限矩阵写在配置里，不做动态配置界面）：
   - `admin` 系统管理员：用户管理、角色分配、临时授权审批、审计查询、模板维护。
   - `senior` 主任医师：拥有普通医生全部权限 + 病历审阅批准。
   - `junior` 主治/住院医师：患者管理、问诊、病历书写、发起会诊、健康管理。
3. 数据范围：用户表带 `department` 字段，患者查询默认过滤本科室（admin 不受限）；会诊通过 `temp_grant` 表开例外口子。
4. 临时授权：`temp_grant(grantee_id, patient_id, reason, expire_at)`，APScheduler 每分钟扫描过期记录自动失效。

### 3.2 模块二：患者信息管理（完整实现）

**需求要点**：多维检索（姓名/ID/症状/日期）、完整档案（基本信息/病史/过敏/治疗方案）、患者分组。

**分析理解**
- 患者档案是全平台数据核心，模块 3~6 都围绕它展开。
- "症状可搜索"要求病史带结构化标签字段（`symptom_tags`），而非纯文本。

**落地设计**
1. 患者列表：姓名模糊 + 患者 ID 精确 + 症状标签 + 入院日期区间的**组合搜索**，分页。
2. 患者详情：基本信息、病史时间线、**过敏记录醒目红色警示条**、治疗方案。
3. 分组：手动创建分组 + 勾选成员（不做动态规则分组），支持按分组筛选。

### 3.3 模块三：在线问诊（图文核心 + 视频加分）

**需求要点**：图文/视频多渠道、会话录像、记录管理。

**分析理解**
- 原始需求里这是实现难度最高的模块（实时音视频 + 录制）。课程项目策略：**图文做扎实，视频走集成**。

**落地设计**
1. 问诊工作台：医生看到问诊请求列表（状态：待接诊/进行中/已结束）。
2. 图文会话：FastAPI WebSocket 实时收发；支持发图片（本地磁盘存储，返回 URL）；按会话保存全部消息。
3. 视频通话（加分项）：集成腾讯云 TRTC Web SDK（有免费试用额度，官方 Demo 改造成本约 1-2 天）；只保存通话元数据（开始/结束时间、时长）。
4. 记录中心：按患者/日期/关键词检索历史问诊记录。

### 3.4 模块四：电子病历 EMR（核心亮点，完整实现）

**需求要点**：结构化模板、医嘱管理（实时校验）、分级审阅。

**分析理解**
- "分级审阅"体现临床治理：住院医师书写 → 主任医师审签 → 归档锁定。
- 归档后不可直接修改（医疗合规基本要求），修订走"补记"并关联原版本。
- 医嘱校验是演示亮点：开药时自动比对过敏史 + 剂量范围。

**落地设计**
1. 病历编辑器：选模板（如"入院记录"）→ 按模板字段填写（表单生成）→ 暂存/提交。
2. 模板管理：预置 2-3 个模板（管理员可增删改，字段用 JSON 定义）。
3. 医嘱：开立/修改/停用；开立时校验——①药品在患者过敏列表中 → **红色拦截**；②剂量超常规范围 → **黄色警告**。
4. 审阅流程：`senior` 待审列表 → 通过（归档，只读）/ 退回（附意见）。
5. 版本留痕：每次提交存版本号，归档后只能新增"补记版本"。

### 3.5 模块五：远程会诊（简化实现）

**需求要点**：请求管理、资料共享、多学科协作、报告生成。

**分析理解**
- 会诊与问诊共享聊天能力，但业务流不同：问诊是"医生↔患者"，会诊是"多医生围绕某患者"。
- 与模块 1 联动：受邀专家获得**临时数据权限**，会诊结束自动回收——这正是"临时权限"的最佳演示场景。
- 会诊是状态机：发起 → 受邀确认 → 进行中 → 报告生成 → 归档。

**落地设计**
1. 发起：选患者 + 选专家（可多选）+ 会诊目的 + 上传共享资料。
2. 会诊室：多人聊天室（复用 WebSocket，房间模式）+ 资料下载。
3. 报告生成：会诊结束后，表单填写各位专家意见 + 结论 → 用 Jinja2 模板渲染成报告页（浏览器打印为 PDF）。**不做复杂自动化，模板渲染即视为"自动生成"**。
4. 权限联动：发起时自动给每位受邀专家建 `temp_grant`（有效期 = 预计会诊时间 + 24h 缓冲）。

### 3.6 模块六：患者健康管理（简化实现）

**需求要点**：个性化方案、实时监测、自动提醒、定期评估。

**落地设计**
1. 健康方案：为患者创建计划（用药/复诊/饮食运动建议），表单 + 列表展示。
2. 体征监测：手动录入血压/血糖/心率（带一个模拟数据脚本方便演示），**ECharts 折线图**展示趋势，超出阈值标红。
3. 自动提醒：医生给患者配置提醒规则（如"每天 8:00 服药提醒"），APScheduler 生成站内提醒记录；演示时工作台红点 + 提醒列表。
4. 定期评估：简单表单（填写评估结论 + 方案调整），存档后可在患者详情页查看历史评估。

### 3.7 模块七：医生协作社交（本期不做，保留设计）

PPT 标注 Optional。本质是"内部专业论坛"（帖子+评论+点赞+私信+举报），技术不难但工作量约为整个问诊模块。**结论：本期不做**，答辩口径："因社交模块与核心诊疗流程相对独立且需求标注 Optional，为保证核心模块完成质量，列为二期规划。"（本文档 3.7 节即为其设计保留。）

核心设计要点（供二期）：病例分享必须手动脱敏后发布、与患者数据库物理隔离、模块可整体关闭。

### 3.8 模块八：操作日志与审计（简化实现，必做）

**需求要点**：全量日志（不可篡改）、系统监控、审计报表。

**落地设计**
1. 日志埋点：FastAPI 中间件统一记录——谁（user_id）、何时、IP、做了什么（method+path+动作语义）、对哪个对象、成功与否。写操作（POST/PUT/DELETE）必记，敏感查询（查看患者详情）也记。
2. 防篡改：日志表只 INSERT；用数据库账号权限禁止该表的 UPDATE/DELETE（答辩演示点）。
3. 查询与报表：admin 按"用户 / 时间范围 / 操作类型"检索，一键导出 CSV。
4. 系统监控（简化）：管理端一个统计面板——用户数、今日活跃、问诊量、日志条数、服务运行时长。不做 Prometheus 等企业级监控。

### 3.9 模块九：用户体验（全局约束）

| 要求 | 落地手段 |
|------|---------|
| 流畅 | 前后端分离 SPA；列表全部分页；图片懒加载；FastAPI 异步接口 |
| 数据完整 | 数据库事务；外键约束；定期 mysqldump 备份脚本 |
| 数据安全 | JWT 鉴权全接口覆盖；密码 bcrypt 加盐哈希；身份证/手机号字段加密存储、页面脱敏展示（138\*\*\*\*1234）；HTTPS（演示可用自签证书） |

## 4. 角色与核心流程

### 4.1 用户角色（3 + 1）

| 角色 | 职责 | 关键操作 |
|------|------|---------|
| `admin` 系统管理员 | 平台治理 | 用户/角色分配、临时授权管理、模板维护、审计日志与报表、统计面板 |
| `senior` 主任医师 | 临床治理 | 全部医生权限 + **病历审阅批准** + 会诊主导 |
| `junior` 主治/住院医师 | 日常诊疗 | 患者管理、图文问诊、病历书写、医嘱开立、发起会诊、健康方案 |
| （会诊专家） | 临时角色 | 在 temp_grant 有效期内查看指定患者资料、参与会诊、出具意见 |

> 患者端不做。体征数据由医生代录 + 模拟脚本生成，答辩时说明"患者端为二期"。

### 4.2 核心业务流程

**流程 1：日常诊疗主线（演示主线）**

```
登录(密码+邮箱验证码) → 检索患者 → 查阅档案(过敏警示)
  → 发起图文问诊 → 书写病历(模板) → 开立医嘱(过敏拦截演示)
  → 提交审阅 → [切换 senior 账号] 审阅通过 → 归档锁定
```

**流程 2：远程会诊（临时权限演示场景）**

```
junior 发起会诊(选患者+选外科室 senior) → 系统自动创建 temp_grant
  → 专家接受 → 多人聊天室 + 共享资料
  → 填写意见 → 渲染生成会诊报告 → 归档到患者档案
  → temp_grant 到期自动失效（演示：专家账号刷新后已无权限）
```

**流程 3：院外健康管理**

```
制定健康方案 → 录入/模拟体征数据 → ECharts 趋势监测(异常标红)
  → 配置提醒规则 → 站内提醒记录 → 定期评估 → 调整方案
```

**贯穿全程**：所有写操作自动进审计日志，admin 可查可导出。

## 5. 初步设计

### 5.1 技术选型（已定）

| 层次 | 选型 | 说明 |
|------|------|------|
| 后端 | **Python 3.11 + FastAPI** | 异步高性能；**自动生成 OpenAPI 文档（/docs）**——前后端协作利器，答辩演示加分 |
| ORM | SQLAlchemy 2.0 + Pydantic v2 | 类型安全的模型与校验 |
| 认证 | JWT（pyjwt）+ bcrypt 密码哈希 | Redis 存验证码 + JWT 黑名单（登出失效） |
| 数据库 | **MySQL 8** | 业务数据 + 审计日志同库 |
| 缓存 | **Redis 7** | 验证码、JWT 黑名单、WebSocket 在线状态、首页统计缓存 |
| 定时任务 | APScheduler | 临时权限到期回收、提醒规则触发 |
| 前端 | **Vue 3 + Vite + Element Plus + Pinia + Axios + ECharts** | 组件库成熟，医疗后台类页面开发快 |
| 实时通信 | FastAPI 原生 WebSocket | 图文问诊、会诊聊天室 |
| 文件存储 | 本地磁盘 `uploads/`（FastAPI StaticFiles 提供） | 问诊图片、会诊资料；不引入 MinIO |
| 邮件 | smtplib（QQ/163 邮箱 SMTP） | 登录验证码 |
| 视频（加分） | 腾讯云 TRTC Web SDK（免费试用） | 官方 Demo 集成 |
| 报告导出 | Jinja2 模板渲染 + 浏览器打印 PDF；审计报表 CSV | 不引入重型 PDF 库 |
| 部署 | 本地/单服务器：Nginx 反代（可选）+ MySQL + Redis + Uvicorn | docker-compose 可选，不强求 |

### 5.4 关键设计决策

| # | 决策点 | 方案 |
|---|--------|------|
| 1 | 权限模型 | **写死的 3 角色矩阵**（装饰器/依赖注入检查角色）+ 科室字段过滤数据范围 + `temp_grant` 临时授权表。不做动态权限管理 |
| 2 | 病历存储 | 模板字段值存 JSON（`content_json`），前端按模板定义动态渲染表单 |
| 3 | 病历版本 | 每次提交 version+1 全量快照；`archived` 状态只读，修订另存新版本关联原病历 |
| 4 | 医嘱校验 | 开立时同步校验：过敏药品 → blocked（拦截）；剂量超限 → warning（可确认后继续）。校验规则写死在配置/代码 |
| 5 | 审计 | FastAPI 中间件拦截写请求 + 关键读接口手动埋点；日志表 INSERT ONLY |
| 6 | 鉴权 | JWT（2h）+ Redis 黑名单实现登出；所有路由通过依赖注入校验角色 |
| 7 | 聊天 | WebSocket 房间模式，`consultation_id`/`meeting_id` 即房间号；历史消息走 REST 分页查询 |
| 8 | 敏感字段 | bcrypt 存密码；手机号/身份证 AES 加密（密钥放环境变量），前端脱敏展示 |
| 9 | 会诊临时权限 | 发起会诊 → 自动为每位受邀专家插 `temp_grant`（expire = 24h 后）；APScheduler 每分钟置 `is_valid=0` |

### 6.1 分工建议（后端 3 人 + 前端 2 人 + 组长全栈 1 人）

| 成员 | 定位 | 负责模块 | 关键交付 |
|------|------|---------|---------|

| B | 后端 | **患者中心 + EMR**：患者 CRUD/搜索/分组、模板、病历版本与审阅状态机、医嘱校验 | 患者 + 病历全部接口 |
| C | 后端 | **问诊 + 会诊**：WebSocket 房间、消息持久化、问诊/会诊状态机、资料上传、Jinja2 报告渲染；（加分）TRTC 接入 | 聊天室 + 会诊流程接口 |
| D | 后端 | **健康管理 + 统计**：方案/体征/提醒规则/评估、APScheduler 提醒任务、造数脚本、管理端统计接口 | 健康管理接口 + ECharts 数据 |
| E | 前端负责人 | **前端架构 + 工作台 + 患者中心 + 问诊 UI**：Vite 项目搭建、路由/Pinia/权限指令、布局与菜单、患者列表/详情（Tab 复用）、聊天室组件 | 可用的整体前端骨架 |
| F | 前端 | **病历 + 会诊 + 健康管理 + 管理端 UI**：模板动态表单渲染、审阅页、医嘱校验弹窗、会诊页、ECharts 图表、admin 各页面 | 病历编辑器（前端难点） |
