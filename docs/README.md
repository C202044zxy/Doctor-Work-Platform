## 权威顺序

同一件事只由一份文档说了算：

1. **任务、编号、负责人、状态、排期、技术选型、部署方式** → `01-任务安排.md`
2. **测试场景、演示基线、模拟红线、答辩口径** → `02-测试场景.md`
3. **字段名、枚举值、状态码等字段级契约** → `api/openapi.yaml`（`api/API-索引.md` 是它的中文索引）
4. **"现在到底建成了什么"** → 代码，其次是 `03-实现现状.md`

冲突时的处理：**代码事实优先于任何文档**，发现文档与代码不符，改文档而不是改事实描述；字段口径冲突时以 `openapi.yaml` 为准。

## 三个最容易踩的坑

1. **`openapi.yaml` 描述的是目标态，不是现状。** 它声明 77 条路径，其中只有 17 条有实现。`/api/users`、`/api/emr/*`、`/api/consultations*`、`/api/meetings*`、`/api/audit-logs*`、`/ws/chat/{room_id}` 等**都还没有代码**。详见 `03-实现现状.md` §5。
2. **人脸登录是模拟。** `backend/app/face_login.py` 的 `match_face()` 恒返回 `True`，且该路由在匿名白名单里——任意合法 JPEG 加一个存在的活跃用户名就能换到真实的 2 小时 token。任何文档、页面、答辩口径都必须把它标为模拟，**绝不可对外部署**。
3. **旧编号已作废。** `T01–T37`、`M01–M07` 与单字母成员代号（A–F）**只允许出现在 `01-任务安排.md` §7 的对照表里**，不得出现在分支名、PR 描述、新文档中。

> ⚠️ **只剩一份没删：仓库根的 `新任务安排.md`。** 它也是旧文档（把 M0 / M1 / M2 标为"已完成"，把 WebSocket、视频通话标为已交付，科室名还是中文），**不要拿它做任何判断**，只当它不存在。它尚未删除只因删除操作没拿到权限；由有权限的人用 `git rm 新任务安排.md` 清掉即可。

删除的原因：它们互相矛盾，且有几份自称"唯一权威来源"，却把从未实现的模块（WebSocket、图文消息、会诊、体征）标为"已完成"。**留一份"只作溯源"的副本，等于留一份随时会被误读的第二权威来源。**

**不要再去引用它们。** 需要旧编号的追溯，只用 `01-任务安排.md` §7.1 的映射表；需要历史版本，用 `git log`。`docs/01` – `docs/03` 与 `docs/api/` 是自包含的。

## 维护约定

- **合并 PR 时同步更新 `01-任务安排.md` §2 的状态列。** 无代码不得写 `已完成`；有代码但测试场景未逐条跑过，最多 `部分完成`；模拟实现一律加"（模拟）"。
- **契约变更必须同一个 PR 内改三处**：`api/openapi.yaml`、`api/API-索引.md`、实现。
- **发现文档与代码不符，立即改文档**，并在 `03-实现现状.md` 校准相关数字。
- 不要再新增并列的"权威"文档。有新内容就并入上述 4 份之一。
